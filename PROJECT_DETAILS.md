# Memory Gallery Project Details

## 1. Project overview

Memory Gallery is a full-stack web application for creating shared memory events, uploading photos, and inviting friends to join private event galleries. The project is split into two main parts:

- Backend: Node.js + Express + MongoDB/Mongoose
- Frontend: Angular app for the dashboard, auth flow, gallery browsing, and invites

The app allows users to:

- register and log in securely
- create events and automatically join as owners
- upload photos to a per-event gallery
- view and delete photos with permission checks
- generate invite codes and join events through invite links
- manage event membership and access control

## 4. Backend architecture

### App entry point
The backend starts in `gallery-backend/index.js`.

It:

- loads environment variables using dotenv
- creates an Express app
- connects to MongoDB with `dbConnect()`
- mounts route groups for auth, events, gallery, and invites
- exposes a health endpoint at `/api/health`

### Main route mounts

#### Auth routes
Base path: `/api/auth`

- `POST /api/auth/register`
- `POST /api/auth/login`

#### Event routes
Base path: `/api/events`

- `POST /api/events` — create an event
- `GET /api/events` — list events for the current user
- `GET /api/events/:eventId` — fetch a single event
- `DELETE /api/events/:eventId` — delete an event (owner-only)

#### Gallery routes
Mounted under `/api/events`

- `GET /api/events/:eventId/photos`
- `POST /api/events/:eventId/photos`
- `DELETE /api/events/:eventId/photos/:photoId`

#### Invite routes
Mounted at `/api`

- `POST /api/events/:eventId/invite`
- `POST /api/invites/:code/join`

## 5. Auth and authorization model

### JWT auth
Authentication is handled with a JWT generated by `generateToken.js`.

Token payload includes:

- `id`
- `name`
- `email`

The token is expected to be sent as:

```http
Authorization: Bearer <token>
```

### Middleware
`middleware/auth.js` verifies the token and attaches `req.user` with:

```js
{ id, name, email }
```

Routes that require login use `requireAuth` before the controller.

## 6. Database models

### User
File: `gallery-backend/models/User.js`

Fields:
- `name` (required)
- `email` (required, unique, lowercase)
- `passwordHash` (required)
- `createdAt`

Methods:
- `comparePassword(plainPassword)`

Important behavior:
- password hash is stripped from JSON responses using a Mongoose `toJSON` transform

### Event
File: `gallery-backend/models/Event.js`

Fields:
- `name` (required)
- `date`
- `coverUrl`
- `ownerId` (ref: User, required)
- `createdAt`

Indexes:
- `ownerId: 1`

### EventMember
File: `gallery-backend/models/EventMember.js`

Fields:
- `eventId` (ref: Event, required)
- `userId` (ref: User, required)
- `role` (`owner` or `member`)
- `joinedAt`

Indexes:
- unique composite index on `(eventId, userId)`

### Photo
File: `gallery-backend/models/Photo.js`

Fields:
- `eventId` (ref: Event)
- `uploaderId` (ref: User)
- `url` (required)
- `publicId` (Cloudinary asset id)
- `caption`
- `uploadedAt`

Indexes:
- composite index on `(eventId, uploadedAt)`

### Invite
File: `gallery-backend/models/Invite.js`

Fields:
- `eventId`
- `inviteCode` (unique)
- `createdBy`
- `expiresAt`

## 7. Core backend behaviors

### Registration
`POST /api/auth/register`

Validates:
- name
- email
- password

Behavior:
- checks for duplicate email
- hashes password with bcrypt
- creates user
- returns JWT + user data

### Login
`POST /api/auth/login`

Validates:
- email
- password

Behavior:
- finds user by lowercase email
- compares password with bcrypt
- returns JWT + user data

### Event creation
`POST /api/events`

Behavior:
- validates `name`
- creates event with `ownerId: req.user.id`
- automatically creates an `EventMember` record with role `owner`

### Event list
`GET /api/events`

Behavior:
- finds all memberships for the current user
- returns events matching those membership ids
- sorts by newest first

### Event detail
`GET /api/events/:eventId`

Behavior:
- checks whether current user is a member
- returns event data or denies access

### Event deletion
`DELETE /api/events/:eventId`

Behavior:
- only the event owner can delete
- deletes associated photos, event memberships, invites, and event document
- removes Cloudinary image assets before deleting photo records

### Photo upload
`POST /api/events/:eventId/photos`

Behavior:
- requires the user to be a member
- stores the uploaded photo URL and Cloudinary `publicId`
- optionally sets `coverUrl` if the event has no cover yet

### Photo deletion
`DELETE /api/events/:eventId/photos/:photoId`

Behavior:
- allows either the uploader or the event owner to delete
- removes the Cloudinary asset
- deletes the database record
- updates event cover if the deleted photo was the cover

### Invite generation
`POST /api/events/:eventId/invite`

Behavior:
- only existing members may generate invites
- creates a random invite code
- optional expiry supported via `expiresInDays`

### Invite join
`POST /api/invites/:code/join`

Behavior:
- validates invite code
- checks expiry
- prevents duplicate memberships
- creates a membership with role `member` if the user is not already joined

## 8. Frontend app routing

The Angular router in `gallery-frontend/src/app/app.routes.ts` contains the following routes:

- `/auth` → `AuthComponent`
- `/dashboard` → `DashboardComponent` with `authGuard`
- `/event/:id` → `EventGalleryComponent` with `authGuard`
- `/join/:code` → `InviteJoinComponent` without `authGuard` by design
- default redirect to `/dashboard`

This means invite links can be visited before login, and the invite page can redirect the user to auth if needed.

## 10. Environment variables

The backend expects environment variables to be set in a `.env` file inside `gallery-backend/`.

Typical variables are:

```env
PORT=5000
MONGODB_URI=mongodb://localhost:27017/your-db
DB_NAME=memory-gallery
JWT_SECRET=your-secret-key
CLOUDINARY_CLOUD_NAME=your-cloud-name
CLOUDINARY_API_KEY=your-api-key
CLOUDINARY_API_SECRET=your-api-secret
```

Notes:
- `JWT_SECRET` is required for auth middleware and token generation
- `MONGODB_URI` and `DB_NAME` are required for MongoDB connections
- Cloudinary variables are used for image cleanup and asset management

## 13. Security and access rules

Some important rules in the app:

- only authenticated users can create or view protected resources
- event owners can delete the whole event
- only the uploader or the event owner can delete a photo
- a user cannot join the same event twice
- invite links can expire
- password hashes are never returned in API responses

---

## 14. Notes on implementation style

This project is organized around clear responsibilities:

- routes define URL access
- controllers handle business logic
- models define Mongo schema and validation
- middleware enforces auth
- utilities centralize token generation and Cloudinary integration

The app is designed to keep permission logic and cleanup logic server-side, which is important for a system involving private galleries and media assets.

---

## 15. Summary

Memory Gallery is a private photo-sharing event app where users can create events, invite others, upload images, and share memories within a controlled, authenticated environment. The codebase is structured for a clean separation between frontend presentation, backend API logic, and database persistence.
